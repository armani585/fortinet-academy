MODULE 20 · Expertise · 55 MIN ESTIMÉES

Sauvegarde, mise à jour et retour arrière

Préparer un changement FortiOS avec validation et récupération documentées.

Prérequis : Modules 7, 8 et 14.

01 · Comprendre02 · Approfondir03 · AppliquerRepères GUI / CLIExercice corrigéQuizSources

LEÇON 1 / 3

Une sauvegarde doit être restaurable

Conserve une configuration identifiée par équipement, version, date et périmètre Global/VDOM. Protège le fichier et le mot de passe de chiffrement. Une sauvegarde anonymisée destinée au partage n’est pas nécessairement suffisante pour restaurer les secrets. Vérifie l’existence et la lisibilité du fichier, puis exerce la récupération sur un environnement adapté.

LEÇON 2 / 3

Préparer le chemin de versions

Lis les notes de la version cible et le chemin de mise à niveau officiellement pris en charge pour le modèle et la version de départ. Certaines étapes intermédiaires sont nécessaires. Vérifie compatibilité Fabric, fonctions retirées ou modifiées et problèmes connus. Une version plus récente n’est pas automatiquement le bon choix pour toutes les productions.

LEÇON 3 / 3

Définir succès et échec

Avant le changement, capture état HA, tunnels, routes et tests applicatifs. Fixe une durée maximale de diagnostic avant retour arrière. Une rétrogradation peut nécessiter l’image et la configuration correspondant à la version précédente ; ne suppose pas qu’une configuration convertie sera réversible. Après mise à jour, contrôle erreurs de configuration, licences, connectivité et journaux, puis archive les preuves.

Se repérer dans FortiOS

Dans la GUI

Menu du compte → Configuration → Backup ; gestion du firmware dans les vues système/Fabric selon version.

Dans la CLI

get system status
get system ha status
diagnose debug config-error-log read

Lecture des états et erreurs de conversion. Leur interprétation se fait avec les notes de version et la configuration de référence.

Exemple expliqué

Un équipement fournit du SSL VPN tunnel sur une version antérieure. Le passage vers 7.6.3 implique de traiter sa migration vers IPsec avant la fenêtre de changement, pas de découvrir le retrait après redémarrage.

À toi de pratiquer

Travaille dans un laboratoire isolé. Si tu n’as pas le matériel requis, rédige les observations attendues ; cela ne remplace pas une validation réelle.

  1. Rédige un plan pour un modèle et une version de laboratoire réellement identifiés.
  2. Sauvegarde la configuration chiffrée, documente le chemin d’upgrade et prépare les tests avant/après.
  3. Simule sur papier l’échec d’un service critique et décris les fichiers, accès et décisions nécessaires au retour arrière.
Afficher le corrigé de l’exercice

Un plan complet indique point de départ exact, version cible, étapes, sauvegardes, accès de récupération, critères mesurables et personne décidant le rollback. Aucun saut de version ne doit être deviné.

Erreur fréquente

Valider la mise à jour parce que la GUI répond, sans tester VPN, annuaire, routes, logs et applications.

VÉRIFIER SES ACQUIS

Quiz du module 20

Trois questions, un point par réponse correcte. Tu peux réessayer sans limite. Une réponse non renseignée est signalée séparément ; elle ne rapporte pas de point.

1. Peut-on toujours installer directement n’importe quelle version plus récente ?

2. Quel document indique notamment les changements et problèmes connus d’une version ?

3. Quel est un critère de succès suffisant ?

Consulter le corrigé du quiz

1. Peut-on toujours installer directement n’importe quelle version plus récente ?
Réponse : Non, il faut suivre le chemin pris en charge. Le chemin dépend du modèle et de la version de départ.

2. Quel document indique notamment les changements et problèmes connus d’une version ?
Réponse : notes de version. Les notes de version accompagnent l’analyse du chemin de mise à jour.

3. Quel est un critère de succès suffisant ?
Réponse : Les tests métier et états prévus sont validés. La disponibilité de la GUI ne valide pas l’ensemble des services.
